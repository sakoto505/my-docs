# 我的技术文档

欢迎访问我的个人文档网站。本网站使用 **MkDocs** 构建，通过 **GitHub Actions** 自动部署到 **GitHub Pages**。

- 作者：sakoto505
- 实践主题：静态文档的自动化构建与发布
- 课程：开源软件开发实践

## 这个网站想解决什么问题

写文档最麻烦的往往不是"写"，而是"发布"。以前我会把 Markdown 文件直接丢到仓库里，读者要么下载
下来自己看，要么等有人手工导出成网页。文档一多，格式不统一、目录对不上、链接失效就成了常态。

这次实践想验证一件事：**只要我提交 Markdown，网站就应该自己变**。于是我把整个发布链路搬到了
GitHub Actions 上——本地只负责内容和预览，构建与部署交给云端。

## 一条命令带来的变化

本地预览只需要一条命令，它会在保存文件时自动刷新浏览器：

```bash
python -m mkdocs serve
```

推送之后，则是另一条链路在替我干活：

```bash
git add docs/index.md
git commit -m "更新首页说明"
git push origin main
```

## 我的实践体会

1. **内容与产物分离**是这个方案最舒服的地方。`docs/` 是源码，`site/` 是产物；产物永远由
   构建生成，我不会去手改它，也就不会出现"本地改好了、线上还是旧版"的错位。
2. **`--strict` 是个好习惯**。它在警告时直接让构建失败，把"某个页面没被导航引用""链接写错"
   这类小问题拦在部署之前。
3. **自动化真正省下的不是时间，而是注意力**。不用记住"发版要先 build 再 deploy"，只要记得
   push，剩下的流程由工作流固定下来。
